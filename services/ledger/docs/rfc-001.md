# RFC-001: Ledger service design

**Status: LOCKED for v1.** Waiting for independent review (see the end).

Related: `docs/prd.md` (what), `docs/invariants.md` (rules), `docs/versions.md` (later), `docs/decisions/` (why), and at the repository root `docs/architecture-assessment.md`.

## Summary

One service, one PostgreSQL database. It stores accounts, transactions, and entries in an append-only, double-entry model. The database enforces the rules. Other services use it over HTTP. It knows nothing about providers, webhooks, payouts, or statements.

## Scope and boundaries

In scope: clients and authentication, currencies, accounts, transactions, reversals, balances, idempotency, queries, `verify`, and operations.

Out of scope here (other services, not designed yet): payment providers, webhooks, payouts, statements, and reconciliation. The ledger only gives them what they need:

- `external_ref` to link a transaction to their event (DEC-0014).
- `Idempotency-Key` so they can retry safely (DEC-0005).
- A read API that never skips a committed row (DEC-0019).
- Scoped, revocable credentials (DEC-0013).

Account conventions are the **callers'** business. For example, a gateway may create an asset account for money held at a provider, and a liability account for each user wallet. The ledger sees only accounts.

## Architecture

```
  Client services (HTTP + JSON, Bearer API key)
              |
              v
   +--------------------------+
   |  Ledger service (Fastify)|   no outbound calls
   |  auth -> validate -> post|
   +------------+-------------+
                |  SQL as role ledger_app (limited)
                v
   +--------------------------+
   |  PostgreSQL 17+          |   owner role: ledger_migrator
   |  currencies, clients,    |   constraints, triggers, grants
   |  accounts, transactions, |
   |  entries, idempotency    |
   +--------------------------+
```

Operator tools (`npm run migrate`, `client:*`, `verify`) run outside the service with their own roles.

## Roles and privileges (DEC-0016)

| Role | Used by | Can do |
| ---- | ------- | ------ |
| `ledger_admin` (superuser) | `db:bootstrap` only | Create the two roles below |
| `ledger_migrator` | Migrations, operator tools | Owns everything |
| `ledger_app` | The running service | Only what the grants below allow |

`ledger_app` grants (written in migrations, never broader):

| Table | Privileges |
| ----- | ---------- |
| `currencies` | `SELECT` |
| `clients` | `SELECT` |
| `accounts` | `SELECT`, `INSERT`, and `UPDATE (debits_total, credits_total, version)` |
| `transactions` | `SELECT`, `INSERT` |
| `entries` | `SELECT`, `INSERT`, and use of its sequence |
| `idempotency_keys` | `SELECT`, `INSERT`, and `UPDATE (response_code, response_body, transaction_id)` |

Role defaults: `statement_timeout` 10 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 15 s, `transaction_timeout` 20 s.

## Data model

Amounts are `bigint` minor units (DEC-0008). Currency is a 3-letter code from the allow-list. The ledger has no `DELETE` for any table.

```sql
CREATE TABLE currencies (
  code           char(3) PRIMARY KEY CHECK (code ~ '^[A-Z]{3}$'),
  minor_exponent smallint NOT NULL CHECK (minor_exponent BETWEEN 0 AND 4)
);
-- A migration seeds: NGN, USD, EUR, GBP, GHS, KES, ZAR (all exponent 2).

CREATE TABLE clients (
  id          uuid PRIMARY KEY,
  name        text NOT NULL UNIQUE,
  key_prefix  text NOT NULL,
  key_hash    bytea NOT NULL UNIQUE,
  scopes      text[] NOT NULL
                CHECK (cardinality(scopes) > 0
                       AND scopes <@ ARRAY['ledger:read','ledger:write']::text[]),
  status      text NOT NULL DEFAULT 'active' CHECK (status IN ('active','revoked')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  revoked_at  timestamptz,
  CHECK ((status = 'revoked') = (revoked_at IS NOT NULL))
);

CREATE TABLE accounts (
  id             uuid PRIMARY KEY,
  client_id      uuid NOT NULL REFERENCES clients(id),
  name           text NOT NULL,
  kind           text NOT NULL CHECK (kind IN
                   ('asset','liability','equity','revenue','expense')),
  normal_balance text NOT NULL CHECK (normal_balance IN ('debit','credit')),
  currency       char(3) NOT NULL REFERENCES currencies(code),
  allow_negative boolean NOT NULL DEFAULT false,
  external_id    text,
  debits_total   bigint NOT NULL DEFAULT 0 CHECK (debits_total >= 0),
  credits_total  bigint NOT NULL DEFAULT 0 CHECK (credits_total >= 0),
  version        bigint NOT NULL DEFAULT 0,
  created_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (id, currency),
  UNIQUE (client_id, external_id),
  CONSTRAINT no_overdraft CHECK (
    allow_negative OR
    (CASE normal_balance
       WHEN 'debit'  THEN debits_total - credits_total
       ELSE               credits_total - debits_total
     END) >= 0)
);

CREATE TABLE transactions (
  id                      uuid PRIMARY KEY,
  client_id               uuid NOT NULL REFERENCES clients(id),
  kind                    text NOT NULL CHECK (kind IN ('transfer','reversal')),
  description             text,
  metadata                jsonb NOT NULL DEFAULT '{}',
  external_ref            text,
  reverses_transaction_id uuid UNIQUE REFERENCES transactions(id),
  created_at              timestamptz NOT NULL DEFAULT now(),
  UNIQUE (client_id, external_ref)
);

CREATE TABLE entries (
  seq            bigserial PRIMARY KEY,
  id             uuid NOT NULL UNIQUE,
  transaction_id uuid NOT NULL REFERENCES transactions(id),
  account_id     uuid NOT NULL,
  currency       char(3) NOT NULL,
  direction      text NOT NULL CHECK (direction IN ('debit','credit')),
  amount         bigint NOT NULL CHECK (amount > 0),
  created_at     timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (account_id, currency) REFERENCES accounts (id, currency)
);
CREATE INDEX entries_account_seq ON entries (account_id, seq);
CREATE INDEX entries_transaction ON entries (transaction_id);
CREATE INDEX transactions_created ON transactions (created_at, id);

CREATE TABLE idempotency_keys (
  client_id      uuid NOT NULL REFERENCES clients(id),
  key            text NOT NULL,
  request_hash   text NOT NULL,
  response_code  int,
  response_body  jsonb,
  transaction_id uuid REFERENCES transactions(id),
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (client_id, key)
);
```

Notes:

- A `UNIQUE` constraint treats `NULL` values as distinct, so many accounts may have no `external_id` and many transactions may have no `external_ref`.
- Identifiers (`id`) are UUIDs created by the service.
- `created_at` comes from the database clock. Clients cannot set it.
- Balance of an account: debit-normal is `debits_total - credits_total`. Credit-normal is `credits_total - debits_total`.

### Database protections

- **Immutability (INV-02).** `BEFORE UPDATE OR DELETE` triggers on `entries` and `transactions` raise an error. The app role has no such privilege either. Two layers.
- **Balanced (INV-03, INV-04).** A deferred constraint trigger runs at commit for each transaction. It checks: at least 2 entries, at least one debit and one credit, one currency, and total debits equal total credits.
- **Currency match (INV-04).** The composite foreign key `(account_id, currency)` ties each entry's currency to its account's.
- **No overdraft (INV-06).** The `no_overdraft` CHECK on `accounts`.
- **Reversal once (INV-08).** `UNIQUE (reverses_transaction_id)`. A trigger also refuses a reversal of a reversal.
- **Reference unique (INV-13).** `UNIQUE (client_id, external_ref)`.

## Authentication (DEC-0013)

- Header: `Authorization: Bearer <key>`. A key looks like `lk_<43 characters>`.
- The service hashes the key (SHA-256) and looks up an **active** client by `key_hash`. No match gives 401 with a generic message.
- A route needs a scope. A client without it gets 403.
- `/health` and `/health/ready` are public. Everything else needs a key.
- The request logger redacts the `Authorization` header. A test proves it (INV-14).
- Operator tools create and revoke clients. A new key is printed once and never stored.

## Posting a transaction

One database transaction at `READ COMMITTED`:

1. **Authenticate** and check the `ledger:write` scope.
2. **Validate** the request shape. Amounts are digit strings greater than zero. There are 2 or more entries. All accounts are listed.
3. **Begin.**
4. **Claim the idempotency key.** `INSERT ... ON CONFLICT DO NOTHING` on `(client_id, key)`.
   - Inserted: continue.
   - Not inserted: an earlier request committed this key. If `request_hash` differs, return 409 `idempotency_key_reused`. If it matches, return the stored response and stop.
   - If another request holds the same key mid-write, this insert waits on the unique index until that request commits or rolls back. No "in progress" state is needed.
5. **Lock** the touched accounts: `SELECT ... FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE`. Check that all exist.
6. **Insert** the transaction row and its entries.
7. **Update totals.** For each account, add the debit and credit sums and set `version = version + 1`. If the CHECK fails, roll back and return 422 `insufficient_funds`.
8. **Store the response** on the idempotency row.
9. **Commit.** The deferred trigger checks balance. A failure here means an app bug. Log it loudly and return 500.

Rules:

- **Lock order (DEC-0003).** Always sort by account ID. This prevents deadlocks between our own transactions.
- **Failed requests are not stored (DEC-0005).** The rollback removes the key row. A retry re-runs the request.
- **No network calls inside this transaction (INV-10).**
- **Error mapping.** `40P01` (deadlock) and `55P03` (lock timeout) give 503 `busy` with `Retry-After`. The client retries with the same key. `25P04` (transaction timeout) gives 503 too. Everything unknown gives 500.

## Reversals

`POST /v1/transactions/{id}/reverse`:

1. Load the original. Reject if it is itself a reversal (422).
2. Post a new transaction with the same entries and the directions swapped. Set `reverses_transaction_id`.
3. The unique constraint means a second reversal fails with 409 `already_reversed`.
4. A reversal can fail for low funds. For example, reversing a deposit after the money was spent. The API returns `insufficient_funds` with a clear message. Fixing that is a separate, manual transaction.

## Balances and verify

- `GET /v1/accounts/{id}/balance` reads the cached totals. It takes no lock.
- The `verify` command (`npm run ledger:verify`) runs read-only, as the app role. It checks:
  1. For every account, `debits_total` and `credits_total` equal the sums over `entries`.
  2. Per currency, total debit-normal balances equal total credit-normal balances.
  3. Every transaction balances.
- It exits non-zero on the first failure and prints the account or transaction.
- `verify` runs at the end of every integration test and in CI.

## Reading safely (DEC-0019)

- **Entries of one account:** ordered by `seq`, cursor-based. Safe, because writes to one account hold its row lock until commit.
- **Global transaction list:** filters on `created_at` and `id`, cursor-based, and returns only rows with `created_at <= now() - lag` (default 30 s). The response carries `as_of`. The role's `transaction_timeout` of 20 s guarantees that older rows are final.
- **Lookups:** by ID, and by `external_ref` (scoped to the calling client's own references by default, or any client with `?client=<name>` for readers).

## API (v1)

All paths except health start with `/v1`. All POSTs need `Idempotency-Key`. Amounts are digit strings. The full contract is `openapi/ledger.v1.yaml`.

| Method and path | Scope | Purpose |
| --------------- | ----- | ------- |
| `GET /health` | none | Liveness (process is up) |
| `GET /health/ready` | none | Readiness (database reachable) |
| `GET /v1/whoami` | any valid key | The calling client's name and scopes |
| `POST /v1/accounts` | write | Create an account |
| `GET /v1/accounts/{id}` | read | Read an account |
| `GET /v1/accounts/{id}/balance` | read | Balance from cached totals |
| `GET /v1/accounts/{id}/entries` | read | Entries, newest first, cursor |
| `POST /v1/transactions` | write | Post a balanced transaction |
| `GET /v1/transactions/{id}` | read | A transaction with its entries |
| `GET /v1/transactions` | read | Lookup by `external_ref`, or a windowed list with watermark |
| `POST /v1/transactions/{id}/reverse` | write | Reverse once |

Error format (all errors):

```json
{ "error": { "code": "insufficient_funds", "message": "...", "request_id": "..." } }
```

| Status | Codes |
| ------ | ----- |
| 400 | `invalid_request` |
| 401 | `unauthorized` |
| 403 | `forbidden` |
| 404 | `not_found` |
| 409 | `idempotency_key_reused`, `already_reversed`, `external_ref_conflict` |
| 422 | `insufficient_funds`, `unbalanced`, `currency_mismatch`, `unknown_currency`, `not_reversible` |
| 503 | `busy` (retry with the same key) |
| 500 | `internal_error` |

## Testing strategy

Integration tests use a real PostgreSQL. Every test that writes ends with `verify`.

- **Property-based.** Random valid transactions check INV-01 to INV-04 and INV-09. Compare with a simple in-memory model.
- **Concurrency.** Many parallel transfers on a few busy accounts. No negative balance, no deadlock, `verify` passes. Run many times.
- **Idempotency.** The same request in 50 parallel calls. The same key with a different body.
- **Immutability.** Try `UPDATE` and `DELETE` as the app role, and as a trigger test with the owner role.
- **Atomicity.** Force a failure mid-transaction. Nothing is saved.
- **Auth.** Missing, wrong, revoked, under-scoped keys. Plaintext key absent from the database and logs.
- **Safe paging.** Write while paging. The union of pages equals the truth.
- **Contract.** The spec is valid, routes match, responses validate against schemas.
- **Migrations.** Apply all on an empty database. Forward-only policy.

## Observability (v1)

Structured JSON logs with request ID, client name, and transaction ID. No secrets. Metrics and tracing come in v1.1 (see the launch gate).

## Security notes

- Secrets only in the environment. `.env.example` has fake values.
- Keys are random, hashed, and never logged.
- Parameterized SQL only.
- Three database roles. The service uses the limited one.
- Run behind TLS. Keep the database off the public network.

## Alternatives considered

| Option | Decision |
| ------ | -------- |
| Signed amounts instead of normality | Rejected (DEC-0001) |
| Compute every balance on read | Rejected. Cache plus verify (DEC-0002) |
| Version locking | Rejected. Row locks and a CHECK (DEC-0003) |
| Serializable isolation everywhere | Rejected. Needs retries everywhere. Row locks are simpler |
| Redis for idempotency | Rejected (DEC-0005, DEC-0007) |
| Replaceable pending entries in v1 | Deferred to v1.1 (DEC-0006) |
| One shared API key | Rejected (DEC-0013) |
| Paging a global list by `seq` | Rejected. It can skip rows (DEC-0019) |
| Event sourcing with a message bus | Rejected for v1 |
| TigerBeetle as the store | Deferred to a v4.0 experiment |

## Scaling path (not built in v1)

What v1 does to keep the path open:

- All writes go through one posting function.
- Amounts are `bigint`. Locks are taken in a fixed order.
- The contract is versioned.

What comes later (see `docs/versions.md`): history caches and as-of balances (v2.0), a write-ahead queue, batching, a plan for hot accounts, and sharding (v4.0).

## Known limits (v1)

- A busy account is a bottleneck, because writes to it are serialized.
- One database node. No failover in the code (operations must provide it).
- No pending state, holds, or available balance.
- One currency per transaction. No conversion.
- No backdating or as-of balances.
- Global lists are about 30 seconds behind.
- Clients can all see all accounts. There is no per-client isolation.
- One failed-auth throttle is missing. Rate limiting is planned for v1.1.
- No audit log table yet. Attribution is recorded on each account and transaction.
- No UI.

## Risks

- Lock contention on busy accounts. Measured in the benchmark (S1).
- Code written by an LLM. See P-0007 and the controls there.
- A forgotten grant. It fails loudly (permission denied).

## Questions for the reviewer

1. Are row locks and the CHECK constraint enough to stop overdraft under concurrency? Is a case missing?
2. Is it safe to keep idempotency keys in the same database transaction as the money write?
3. Are the triggers and limited roles enough to make history immutable? Is there a bypass?
4. Is the watermark design (DEC-0019) correct? Can a committed row still be missed?
5. Is the API-key design enough for service-to-service use before real money?
6. Is anything missing that a ledger needs before it holds real balances?
